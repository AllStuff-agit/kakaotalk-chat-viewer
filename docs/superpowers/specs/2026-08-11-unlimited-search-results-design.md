# 무제한 검색 결과 설계

## 목표

검색 결과의 200개 제한을 제거하되 메인 스레드 메모리와 DOM 크기는 일정하게 유지한다. 검색 결과는 최신순으로 제공하고 버튼 없이 카카오톡처럼 연속 스크롤한다. 서버, 유료 서비스, 외부 의존성은 추가하지 않는다.

## 검토한 방식

전체 결과 배열을 메인 메모리에 보관하는 방식은 구현이 단순하지만 흔한 검색어에서 기존 대용량 문제를 다시 만든다. 화면을 내릴 때마다 원본 대화를 재검색하는 방식은 메모리는 적게 쓰지만 오래된 결과로 갈수록 반복 검색 비용이 커진다. 따라서 Worker가 검색을 한 번 수행하고 결과를 IndexedDB에 청크로 임시 저장하는 방식을 사용한다.

## 데이터 흐름

IndexedDB 버전을 올리고 `searchChunks` object store를 추가한다. 새 검색이 시작되면 이전 검색 결과를 지우고, Worker가 원본 `chunks`를 최신순으로 읽어 일치 메시지의 표시용 요약을 500개 단위로 저장한다. 검색 완료 응답은 결과 배열 대신 `{ total }`만 반환한다. `searchRange(start, count)`는 필요한 결과 청크만 읽어 최대 200개를 반환한다. 새 파일이나 새 검색은 이전 검색 작업과 결과를 취소·교체한다.

## 검색 패널

별도 `SearchResultsRenderer`가 검색 결과 수를 고정 높이 가상 트랙에 매핑한다. 현재 위치 주변 최대 200개만 DOM에 만들고, 스크롤 위치가 창의 경계에 접근하면 IndexedDB에서 다음 범위를 가져온다. 빠른 스크롤 중 늦게 도착한 이전 조회 응답은 폐기한다. 결과 클릭은 기존 채팅 가상 스크롤의 메시지 인덱스로 이동한다.

검색 결과 상단에는 전체 결과 수를 표시하며 `최대 200개` 문구를 제거한다. 검색어 강조는 DOM 텍스트 노드와 `<mark>` 요소로 구성해 채팅 파일의 HTML이 실행되지 않도록 한다.

## 오류와 검증

검색 결과 저장 중 용량이 부족하면 기존 저장 공간 오류 안내를 사용한다. 자동 검사는 검색 제한 제거, 범위 조회, 최대 200개 DOM, 빠른 스크롤 경합, HTML 이스케이프를 확인한다. 브라우저 검증은 200개를 넘는 공통 검색어에서 전체 개수, 처음·중간·마지막 이동, 결과 클릭, 네트워크 비전송을 확인한다.
